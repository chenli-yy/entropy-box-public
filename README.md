# Entropy Box — A Knowledge Compiler for Embodied AI

> Compile once, execute everywhere.

The bottleneck in embodied AI is not model capacity — it is knowledge. What a robot
needs to know already exists: in tens of thousands of papers, GitHub repositories,
ROS packages, model hubs, benchmark suites and engineering blogs. It exists as
**prose**, not as structure. A language model can retrieve a passage about inverse
kinematics; it cannot tell you, in a form another program can consume, which four
distinct engineering paradigms solve the problem, what each one's inputs, outputs
and failure modes are, which open-source assets implement each, and what has to be
solved first. Every query re-derives that structure from scratch, and the
derivation is discarded the moment the conversation ends.

Put differently: the bottleneck is not that material is missing — papers,
repositories and open models are abundant. It is that **one task hides a dozen
technical steps and a tangle of dependencies between them**. A model will write a
detector or a controller when told which is needed; it cannot orchestrate the whole
workflow. It is a craftsman who has mastered every part but has never held the chief
engineer's drawing.

**Entropy Box is a knowledge compiler.** It ingests unstructured sources once and
emits a persistent, typed, deduplicated, machine-consumable knowledge artifact
that improves incrementally and is reused indefinitely — the drawing.

This repository is the public face of the project: the paper, the open data, the
reproducible measurement script, and interactive views of the compiled artifact.

## What is in the artifact

A curated three-level taxonomy (15 top-level domains → 416 sub-domains → 2,511 leaf
topics) drives compilation. Each leaf topic is compiled in one transaction into
typed **task chains**, **capabilities** and **assets**, through a three-phase
multi-agent architecture guarded by admission gates.

Live counts are in [`data/measurements.json`](data/measurements.json) and are
regenerated by [`analysis/measure.py`](analysis/measure.py). Compilation is running
unattended, so they rise over time. At the time of writing, on the order of
25,000 capabilities and 6,000 assets, linked by ~100,000 typed edges.

Two things worth knowing about how to read our numbers:

- **Capability counts differ depending on what you count.** Distinct registry
  entities and per-topic record entries are different quantities; the ratio between
  them *is* the deduplication effect. Both are reported.
- **Coverage is a progress reading, not a ceiling.** Roughly a third of the
  taxonomy is not yet compiled.

## The dependency network is derived, not authored

The part worth pausing on: **50,407 capability dependency edges were not written by
hand and were not inferred by a model.** Each task chain's steps already carry a
`next` pointer and the capabilities they require; walking the chains — punching
through pure routing steps that declare no capability — makes the latent ordering
explicit. 7,089 cross-topic hub capabilities fall out of the same traversal, and
those are the ones an orchestrator most needs to get right.

This is the general claim in miniature: compile the structure once, and questions
that would otherwise need multi-step derivation become graph traversals.

## Why compile

| | Query-time derivation | Knowledge compilation |
|---|---|---|
| Where the analysis happens | inside the request | before the request |
| What is produced | prose | a typed graph |
| After the answer | structure discarded | structure persists |
| Global identity | none | registry, deduplicated |
| Consumable by | a reader | a program |

The measurable consequence is **amortization** — the average number of times each
compiled unit is consumed. It is currently ≈1.6, and more informatively it is
*still rising with coverage* rather than saturating: a capability minted for one
topic is available to every topic compiled afterwards, so the artifact becomes a
better deal the more of the domain it covers.

## Two results

**1. Embedding similarity cannot decide duplication.** Using 1,155 adjudicated
near-duplicate pairs as labelled data:

| Path | pairs | true dup. | precision | AUC | 95% CI |
|---|--:|--:|--:|--:|---|
| Embedding (primary) | 508 | 35 | 0.069 | 0.629 | [0.531, 0.722] |
| Lexical (fallback) | 647 | 4 | 0.006 | 0.454 | [0.271, 0.764] |

Once the gate has flagged a pair, the score is far too weak to decide the merge —
and raising the threshold does not fix it (precision barely moves while half the
true duplicates are discarded). A conservative adjudication stage is therefore a
**requirement**, not a safety margin: a system that merges automatically above a
similarity threshold would, at our operating point, be wrong more than nine times
in ten.

Two limits we state rather than bury: the pairs are conditioned on having been
flagged, so this does not estimate the gate's overall discriminative power; and
gate *recall* is unmeasurable here, because nothing labelled the duplicates the
gate never flagged. The lexical row rests on four positives and is not a finding.

**2. Provenance resolvability, proposed as a metric.** Every compiled topic cites
the research documents it was assembled from, and because those are files, the
citation is mechanically checkable. **98.3%** of the artifact's own evidence
citations resolve. Structural validity is routinely checked for generated knowledge
graphs; provenance resolvability is not — and it is cheap, hard to game, and
directly diagnostic of whether an evidence layer is real or decorative. A system
that cannot report it does not have one.

Full capability descriptions are not distributed in bulk for the whole registry. The
nine case studies are complete worked examples so the structure can be inspected
rather than taken on trust.

## How it is built

[`how-it-works/`](how-it-works/) documents the five stages and three gates, and —
more usefully — publishes **the actual research documents for one topic**, including
their retrieval ledgers and negative-results tables. A record that only ever reports
successful retrieval is indistinguishable from a fabricated one, so the tables
recording what was found and then *rejected* are the load-bearing part.

Alongside them: an 85-second unedited recording of the pipeline running, and a
51-second recording of a natural-language goal being decomposed and assembled into a
technical plan with attributed assets and explicit capability gaps.

## What is withheld, and why

The project has had almost no publicity yet, and we would rather not put the most
load-bearing material into the open while that is still true. This release is
deliberately partial, and we would rather say so than let you find the gaps.

**Published in full:** the taxonomy; bilingual names and levels for every capability;
the asset index with upstream sources; the dependency network's structure (nodes,
domains, degrees, topic tags, 50,407 edges); the retrieval golden set; the
adjudication ledger; every reported number plus the script that regenerates them;
nine topics reproduced completely with diagrams and research ledgers.

**Withheld for now:** full capability *descriptions* in bulk — the fields carrying
inputs, outputs, constraints and performance envelopes. Those are the substance, and
what would be worth copying wholesale. They are readable in full for the nine
case-study topics, which is enough to judge whether the structure is real.

**The intention is to open it completely.** What we are building is the compilation
pipeline and the description standard, not a moat around a name list — and a
knowledge layer nobody can inspect is not infrastructure. If you need something that
is not here, for research or a benchmark or an integration, write to us; we are far
more likely to say yes than no.

## Reproducing the measurements

```bash
python analysis/measure.py --repo /path/to/ontology --json measurements.json
```

Reads only the artifact on disk — no GPU, no network, no running service. Rerun as
compilation proceeds.

## Query the artifact

A read-only retrieval endpoint over the evidence corpus is open — no registration,
no client software:

```bash
curl -X POST "$ENTROPY_BOX_API/api/evidence/search" \
  -H "Content-Type: application/json" \
  -d '{"query": "obstacle inflation collision check", "top_k": 5,
       "mode": "hybrid", "rerank": true}'
```

The same endpoint is packaged as an Agent Skill declaration and as an MCP stdio
server. The open endpoint exposes concept-level evidence retrieval; complex task
retrieval, chain assembly and node-level graph queries are implemented but not yet
exposed as an API. See the project site for the current base URL.

## What this is not

- **Not a search engine.** Output is typed entities with declared interfaces and
  the edges between them, intended for a program.
- **Not a RAG system.** RAG derives structure at query time and discards it.
- **Not a vector database.** That is a runtime component. The content is the typed
  edge families. Vectors give you neighbours; they do not give you `precedes`.
- **Not an execution ontology.** We model engineering decisions, not action
  semantics — complementary to KnowRob and IEEE 1872.
- **Not classical knowledge compilation.** We use the term in a source-level
  engineering sense and claim none of the tractability results of the OBDD/d-DNNF
  line of work. The paper says so explicitly.

## Honest status

- Compilation is **in progress**; roughly a third of the taxonomy is uncompiled.
- **The central comparison has not been run.** We argue for compilation and
  quantify amortization, but have not demonstrated better answers than a strong RAG
  or GraphRAG baseline.
- **Retrieval numbers are not published yet.** The harness and golden set exist; a
  valid run does not. We publish the suite rather than a claim.
- **Build cost is unmeasured.** No per-topic time or token accounting exists yet,
  so the economics of front-loading work cannot be reported.
- **74.1% of task chains are purely linear** although the schema supports
  branching. The compiler emits the simplest structure that passes.
