The problem

A language model has no chief engineer's view.

It can write a detector or a control law when you tell it which one you need. It cannot orchestrate the whole workflow on its own — because one task hides a dozen steps and a tangle of dependencies between them.

A craftsman who has mastered every individual part, but has never held the drawing. What we build is that drawing.

Atomic competence, no composition
Writes a detector happily. Cannot deliver “pick up the red cup” end to end.
Blind to dependencies
Perception → localization → planning → control. Which module feeds which, on what interface, is exactly what gets lost.
The route is a black box
Facing a new task, an engineer reads dozens of papers to compare technical routes by trial and error.
Orchestration eats the time
Most hours go into surveying routes and hand-wiring modules — not the algorithm work that matters.

Retrieval compiles on every query. A compiler compiles once.

Amortization is still rising, not saturating.

The average number of times each compiled unit gets consumed currently stands at 1.61, worth 13,936 avoided re-derivations. The curve has not flattened — compilation becomes a better deal the more of the domain it covers.

Architecture

Five stages. The second does the unexpected work.

Stage 01
Data Layer
Papers, open-source projects, technical documentation and engineering practice — extracted, cleaned, aligned, and admitted through gates into a domain ontology.
1,740
topics compiled
Stage 02
Knowledge Graph
Topics → capabilities → assets, each node carrying declared inputs, outputs, prerequisites and performance envelope. The ordering edges are derived mechanically from 5,756 task chains — by walking each chain's next pointers and the capabilities each step declares, punching through pure routing steps. Not authored, not model-inferred: the ordering was already latent, and a traversal makes it explicit.

Retrieval Engine
Hybrid retrieval that runs over the structure rather than over passages, with every hit traceable to the evidence document it came from. Open read-only endpoint, plus Agent Skill and MCP packaging.

What we found

Two results from the system's own records. One is negative — and more useful.

Embedding similarity cannot decide duplication negative
On 1,155 adjudicated near-duplicate pairs: once the gate has flagged a pair, the similarity score carries far too little signal to decide the merge. Raising the threshold does not fix it — precision barely moves while half the true duplicates are discarded. Any system that merges automatically above a threshold would, at our operating point, be wrong more than nine times in ten.

Pairs are conditioned on having been flagged, so this does not estimate the gate's overall discriminative power; recall is unmeasurable from this data. The lexical row rests on four positives and is not a finding. Full note →

The whole negative result in one picture: tightening the gate throws duplicates away without buying precision. Nine sweep points from the embedding path.

Provenance resolvability, proposed as a metric 98.3%
Every compiled topic cites the documents it was assembled from, and because those are files, the citation is mechanically checkable. Structural validity is routinely checked for generated knowledge graphs; provenance resolvability is not — and it is cheap to compute, hard to game, and directly diagnostic of whether an evidence layer is real or decorative. A system that cannot report it does not have one.
Unverified fields are left unverified by design
1,105 fields are explicitly marked unverified rather than filled in, across 16.2% of topic records. We report this as a positive indicator. Given what is actually verifiable about fast-moving open-source projects, zero unverified markers would not indicate a better artifact — it would indicate a pipeline that fills gaps instead of declaring them.

Query it — no key, nothing to install.

A read-only retrieval endpoint over the evidence corpus is open, and packaged as an Agent Skill declaration and an MCP stdio server. Concept-level evidence retrieval is exposed; chain assembly and node-level graph queries are implemented but not yet public.

Integration guide 
curl -X POST "$ENTROPY_BOX_API/api/evidence/search" \
  -H "Content-Type: application/json" \
  -d '{"query": "obstacle inflation collision check",
       "top_k": 5, "mode": "hybrid", "rerank": true}'

Honest status

What we have not established.

This release is deliberately partial and the central experiment has not been run. We would rather say so plainly than let you discover the gaps.

Full scope, limits & disclosure
  • The central comparison has not been run. We argue for compilation and quantify its amortization, but have not demonstrated better answers than a strong RAG or GraphRAG baseline.
  • Retrieval numbers are not published. The harness and the golden set exist; a valid run does not. We publish the suite rather than a claim.
  • Build cost is unmeasured. No per-topic time or token cost is recorded — so the economics of front-loading work cannot yet be reported.
  • Compilation is in progress. Roughly a third of the taxonomy is uncompiled; counts on this page rise over time.
  • 74.1% of chains are purely linear even though the schema supports branching. Nothing yet rewards capturing genuine route divergence.
