A Knowledge Compiler for Embodied AI Towards structured knowledge compilation for robotics foundation models

The bottleneck in embodied AI is not model capacity — it is knowledge. What a robot needs to know already exists, in papers, repositories, ROS packages, model hubs and benchmark suites. It exists as prose, not as structure. Entropy Box compiles it, once, into a persistent typed graph that programs can consume.

The problem is not missing knowledge

It is that a language model has no chief engineer's view.

Most people assume the bottleneck in robotics development is finding material. It is not — papers, repositories and open models are abundant. The real problem is that a single task hides a dozen technical steps and a tangle of dependencies between them. A model can write an object-detection function or implement a control law when an engineer tells it which one is needed. It cannot orchestrate the whole workflow on its own.

Atomic competence, no composition
A model will happily write a detector or a controller, but cannot independently deliver an end-to-end task like “pick up the red cup”.
Blind to dependencies
One simple task spans perception → localization → planning → control → execution. Which module feeds which, and on what data interface, is exactly what gets lost.
The route is a black box
Facing a new task, an engineer reads dozens of papers and compares several technical routes by trial and error. A model cannot hand you a viable route plan.
Orchestration eats the time
Most engineering hours go into surveying routes and hand-wiring modules together — not into the algorithm work that actually matters.

A language model is a craftsman who has mastered every individual part but has never held the chief engineer's drawing. What we build is that drawing.

Why compile

Traditional retrieval compiles on every query. A knowledge compiler compiles once.

Query-time derivation

  • Question
  • Retrieve passages
  • Model derives the structure
  • Answer, in prose
  • Structure discarded — next query redoes it

Knowledge compilation

  • Corpus
  • Compile — gated, offline, auditable
  • Typed persistent graph
  • Retrieve over structure
  • Reasoning & assembly — gaps named explicitly

The measurable consequence is amortization: the average number of times each compiled unit is consumed. It currently stands at —, corresponding to — avoided re-derivations, and — more informatively — it is still rising with coverage rather than saturating. Compilation becomes a better deal the more of the domain it covers.

What we found

Two results measured from the system's own records. One of them is negative, and it is the more useful of the two.

Embedding similarity cannot decide duplication negative result
Using 1,155 human- and agent-adjudicated near-duplicate pairs as labelled data: once the gate has flagged a pair, the similarity score carries far too little signal to decide the merge. And raising the threshold does not fix it — precision barely moves while half the true duplicates are discarded. A conservative adjudication stage is therefore a requirement, not a safety margin. Any system that merges automatically above a similarity threshold would, at our operating point, be wrong more than nine times in ten.

Two limits we state rather than bury: the pairs are conditioned on having been flagged, so this does not estimate the gate's overall discriminative power; and gate recall is unmeasurable from this data, because nothing labelled the duplicates the gate never flagged. The lexical row rests on four positives and is not a finding.

Provenance resolvability, proposed as a metric 98.3%
Every compiled topic cites the research documents it was assembled from, and because those are files, the citation can be checked mechanically. 98.3% of the artifact's own evidence citations resolve to a retrievable document. Structural validity is routinely checked for generated knowledge graphs; provenance resolvability is not — and it is cheap to compute, hard to game, and directly diagnostic of whether an evidence layer is real or decorative. A system that cannot report it does not have one.
Unverified fields are left unverified by design
1,105 fields are explicitly marked unverified rather than filled in, across 16.2% of topic records. We report this as a positive indicator. Given what is actually verifiable about fast-moving open-source projects, zero unverified markers would not indicate a better artifact — it would indicate a pipeline that fills gaps instead of declaring them.

How it works

Four layers. The one that does the unexpected work is the third.

Layer 4 · Application

Workflow orchestration. With the graph in view, the model selects capability modules, orders their execution, handles interface adaptation, and emits a complete plan — with the gaps named.

Layer 3 · Reasoning

Dependency derivation. 50,407 capability dependency edges are derived mechanically from 5,756 task chains, by walking each chain's next pointers and the capabilities each step declares, punching through pure routing steps that carry no capability. 7,089 cross-topic hubs fall out of this — the capabilities that bridge domains, and the ones an orchestrator most needs to get right.

Layer 2 · Knowledge

Typed modelling. Topics → capabilities → assets, each node carrying declared inputs and outputs, prerequisites, performance envelope and applicability. A computable network rather than a document collection.

Layer 1 · Data

Acquisition and structuring. Knowledge extracted from papers, open-source projects, technical documentation and engineering practice, cleaned, aligned and admitted through gates into a domain ontology.

The derivation in Layer 3 is worth pausing on. The dependency network was not authored and was not inferred by a model: the ordering information was already latent in the task chains, and a graph traversal makes it explicit. It is the clearest instance of the general claim — compile the structure once, and downstream questions become traversals.

What it does that retrieval cannot

Unedited screen recording, 51 seconds. A natural-language goal — “how do you keep a legged robot safe going down stairs?” — is decomposed, matched across topics, and assembled into a technical plan whose nodes carry attributed open-source assets. Every asset card opens onto its repository, licence and import path. This is the thing a passage-retrieval system structurally cannot produce: not a paragraph about stair descent, but a plan with named implementations and explicit gaps.

What we are withholding, and why

The project has had almost no publicity so far, and we would rather not put the most load-bearing material into the open while that is still true. So this release is deliberately partial, and we would rather say so plainly than let you discover the gaps.

Published in full
The three-level taxonomy. Bilingual names and levels for every capability. The asset index with upstream sources. The dependency network's structure — nodes, domains, degrees, topic tags, 50,407 edges. The 126-query retrieval golden set. The adjudicated duplicate ledger. Every number we report, plus the script that regenerates them. Nine topics reproduced completely, with their diagrams and research ledgers.
Withheld for now
Full capability descriptions in bulk — the fields carrying inputs, outputs, constraints and performance envelopes. These are the substance of the artifact, and they are what would be worth copying wholesale. You can read them in full for the nine case-study topics, which is enough to judge whether the structure is real.
The intention
Open it completely. The value we are building is the compilation pipeline and the standard, not a moat around a name list — and a knowledge layer nobody can inspect is not infrastructure. We would rather stage the opening than stage a retreat.

If you want access to something specific that is not here — for research, for a benchmark, for an integration — write to us. We are far more likely to say yes than to say no.

Query it

A read-only retrieval endpoint over the evidence corpus is open. No registration, no client software.

curl -X POST "$ENTROPY_BOX_API/api/evidence/search" \
  -H "Content-Type: application/json" \
  -d '{"query": "obstacle inflation collision check", "top_k": 5,
       "mode": "hybrid", "rerank": true}'

The same endpoint is packaged as an Agent Skill declaration and as an MCP stdio server, so external agents can query the artifact directly. The open endpoint exposes concept-level evidence retrieval; complex task retrieval, chain assembly and node-level graph queries are implemented but not yet exposed as an API. See the project site for the current base URL.

What this is not

  • Not a search engine. The output is typed entities with declared inputs, outputs, prerequisites and implementations, plus the edges between them — intended for a program, not a reader.
  • Not a RAG system. RAG derives structure at query time and discards it. A compiler derives it once and keeps it.
  • Not a vector database. That is a component of the runtime. The content is the typed edge families — hierarchy, ordering, implementation. Vectors give you neighbours; they do not give you precedes.
  • Not an execution ontology. We model engineering decisions, not action semantics. Complementary to KnowRob and IEEE 1872, not a replacement.
  • Not classical knowledge compilation. We use the term in a source-level, engineering sense and claim none of the tractability results of the OBDD/d-DNNF line of work. The paper says so explicitly.

Honest status

  • Compilation is in progress and unattended. Roughly a third of the taxonomy is not yet compiled; counts on this page rise over time.
  • The central comparison has not been run. We argue for compilation and quantify its amortization, but we have not demonstrated better answers than a strong RAG or GraphRAG baseline. That experiment needs baselines beside the golden set, and we have not run it.
  • Retrieval numbers are not published yet. The evaluation harness and golden set exist; a valid run does not. We publish the suite rather than a claim.
  • Build cost is unmeasured. The pipeline records no per-topic time or token cost, so the economics of front-loading work — the quantity that actually decides whether compilation is worth it — cannot yet be reported.
  • 74.1% of task chains are purely linear even though the schema supports branching. The compiler emits the simplest structure that passes, and nothing rewards capturing genuine route divergence.
